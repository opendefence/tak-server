The strict agent checks the new WAR and UserManager checksums. Its three instrumented classes (`X509AuthCodec`, `X509Authenticator`, and Spring's `FilterSecurityInterceptor`) have exactly the same bytes and method signatures as the 5.8-84 candidate; the vendor hook check and both fail-closed startup probes passed. The 101 SQL migration resources in the two SchemaManager JARs have identical paths and bytes. This is compatibility evidence for the tested hooks and migrations, not a claim about all vendor behavior.

The only `WEB-INF/classes` references to `getUpdateinterval` are `X509AuthCodec` and `LdapAuthenticator`. A scan of all 363 nested library JARs found only `takserver-common` references, which define the XML field and copy it between configuration objects without unit conversion. In the codec, `getUpdateIntervalMilliseconds()` multiplies the configured integer by 1000, then `doTlsAuth()` adds the result to `lastAuthTime` from `Date.getTime()`. In the LDAP authenticator, the configured integer reaches `AbstractAuthenticator.setUpdateIntervalSeconds()`; `authenticateAsync()` passes that field to `ScheduledExecutorService.scheduleWithFixedDelay()` with `TimeUnit.SECONDS`. The binary therefore treats `updateinterval` as seconds on both paths, and the default is `60`. The second practical test was inconclusive; no LDAP timing service was available in the local cluster. [The plan](implementation-plan.md#ldap-interval-binary-compatibility-follow-up) requires this bytecode check for each future vendor release.

Validation: the local image built; 34 Python tests passed inside it; the 46 policy assertions, hook helper test, strict installation/fail-closed probes, vendor hook check, federation truststore test, and HTTPS keystore test passed. Both Zarf flavor lints and native Kind/integrated renders passed. In the disposable `tak-server-local` Kind cluster, the new schema Job applied zero migrations, grants completed, authenticated HTTPS returned 200, and two TLS connections using the local probe identity exchanged CoT in both directions. The federation truststore hash was unchanged. The persistent CoreConfig changed only its `network` version attribute; its previous copy remains in the owner backup. Test certificates and keys copied to the host for CoT were removed after the check. After the interval correction, the rebuilt image rendered `updateinterval="60"` and passed 34 Python tests. Zarf applied the ConfigMap value `60`; a coordinated StatefulSet restart was required for the Pod to receive it. All three containers then used image `928c617a91e2`, had zero restarts, and passed the authenticated HTTPS smoke check. The local cluster has no LDAP endpoint, so its CoreConfig omits the optional LDAP element.

The local `task tak` now restarts the StatefulSet after Zarf deploy so repeated development runs use current ConfigMap values and the rebuilt local image tag. The local rollback image is the retained 5.8-84 tag `localhost/tak-server:t2-schema-5.8.84`. Do not roll back a populated production database from this local evidence alone: review any data written while release 92 was active, the schema history, and the matching image/identity tuple first. The integrated flavor, an offline published-digest package, a timed LDAP refresh test, and complete strict-mode acceptance remain open.
